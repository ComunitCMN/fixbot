# Принятые решения

Короткая справка для нового разговора: что решено и **почему**. Если начать
новую переписку, достаточно попросить прочитать этот файл и README —
и контекст восстановится.

Каждое решение здесь закреплено тестом. Если правка ломает тест из списка —
это не поломка теста, это попытка отменить решение.

---

## Предметная область

**Агентская фиксация не даёт эксклюзива.** Несколько агентств ведут одного
клиента одновременно, он достаётся тому, кто первым доведёт до депозита.
Поэтому совпадение с чужой агентской фиксацией **не блокирует** — бот
фиксирует и отвечает **зелёным** «работайте». Название конкурента не
раскрывается, только дата.
→ `test_confirm.py::test_other_agency_is_green_and_permissive`

**Блокирует только клиент отдела продаж.** Определяется по воронке
связанной сделки: розничная — блокирует, агентская — нет. Освобождается
после года без активности.
→ `test_verdict.py::test_retail_blocked`, `test_retail_expired_after_year`

**Тон ответов мягкий.** Бот не знает договорённостей между агентством
и застройщиком, поэтому не выносит приговоров «работать нельзя», а
сообщает факт и отправляет к менеджеру.
→ `test_confirm.py::test_retail_blocked_is_polite`

**Срок фиксации 45 дней** — это напоминание, а не блокировка. За 3 дня
до конца агент получает кнопку «Продолжаю работу»; нажал — срок пошёл
заново и в сделку легло примечание. Не нажал — ничего не происходит.
→ `test_agents.py::test_renewal_restarts_term_and_reminder`

## Что видит агент

**Никаких упоминаний CRM и ссылок на карточки.** У сторонних агентств
доступа к CRM застройщика нет, для них это мусор. Включается через
`SHOW_CRM_LINKS=1`.
→ `test_confirm.py::test_confirmed_hides_crm_links_by_default`,
  `test_verdict_texts_have_no_links_by_default`

**Уведомлений о смене этапов нет.** Внутренние названия воронок вроде
«Прогрев» и «Отвал» наружу не выносим. Агент узнаёт только о четырёх
событиях: срок фиксации, появился конкурент, клиент постучался в прямой
отдел, сделка успешно закрыта.
→ `test_agents.py::test_no_stage_change_notifications`

**Формулировки без жаргона.** Не «под маской 100 номеров», а «не хватает
двух последних цифр».
→ `test_confirm.py::test_masked_note_is_plain_language`

## Распознавание

**Правила свободные.** Это рабочие чаты, сюда пишут ради клиентов. Имени
и телефона достаточно, слово «зафиксируйте» не обязательно. Даже один
номер без имени проходит.

Работает это потому, что **запись всё равно идёт по кнопке**: ложное
срабатывание стоит одного проигнорированного сообщения. Отсюда низкий
порог `MIN_CONFIDENCE=0.3` — он намеренный, поднимать не нужно.

**Ключевое различие — чей номер.** Клиентский ловим; номер отдела продаж,
самого агента или из рекламы игнорируем.

Правила лежат в `prompts/fixation.md` обычным текстом и перечитываются
на каждое сообщение — перезапуск не нужен. Промахи чинятся добавлением
примеров, а не правкой кода.

**Контекст соседних сообщений.** Фиксацию часто пишут в два приёма:
сначала номер, потом «зафиксируйте». Бот помнит три последних сообщения
каждого автора за десять минут.
→ `test_context.py`

## Телефоны

**Скрытыми можно оставить максимум две последние цифры.** Сколько это
в абсолютных цифрах — зависит от страны: для России 9 известных из 11,
для ОАЭ 10 из 12.

**Любые страны через libphonenumber.** Своих таблиц кодов нет.

**Проверяются только длины обычных телефонов** — мобильных и городских.
Иначе любой длинный набор цифр подходил бы под служебные номера: строка
`667653892134` превращалась в `+7 667653892134**`.
→ `test_international.py::test_long_garbage_rejected`

**Сравнение симметричное:** маскированный находит полный и наоборот.
→ `test_phones.py::test_compare_prefix_masked_vs_full`

## Архитектура

**Один экземпляр на застройщика.** Общий код, у каждого клиента свой
`.env`, своя база и свой токен бота. Данные физически не смешиваются,
ошибка у одного не роняет остальных. Схема базы содержит `account_id`
на случай перехода к одному процессу, но пока он не нужен.

**Зеркало базы плюс живой запрос.** Зеркало ищет по маскированным
номерам гарантированно (сравнение по цифрам), живой запрос закрывает
слепую зону со свежими контактами. Одно другое не заменяет.

**Авторизация amoCRM за отдельным слоем** (`amoauth.py`): сейчас
долгосрочный токен, OAuth включается переменной и требует домена
с HTTPS. Остальной код о способе входа не знает.

**Две роли.** Оператор держит бота на сервере и видит техническое.
Владелец — застройщик, видит рассылки, группы, агентства, статистику.
Токенов и воронок владелец не видит: это не его слой.
→ `test_menu.py::test_owner_has_no_technical_section`

**Отписка от рассылок отдельно от уведомлений.** `/stop` глушит рассылки,
`/notify off` — уведомления по своим клиентам. Смешивать нельзя: иначе
человек, которому надоела реклама, потеряет то, ради чего подписывался.

## Обязательные шаги при запуске нового клиента

1. **Разметить воронки** — без этого бот отказывается работать.
2. **Завести агентскую воронку**, если её нет. Иначе фиксации бота лягут
   в розничную воронку и через неделю он начнёт блокировать сам себя.
3. **Первую неделю `DRY_RUN=1`** — бот отвечает, но в CRM не пишет.
   Новые клиенты создаются в этом режиме автоматически.

## Как работать с проектом безопасно

**Перед изменениями и после — тесты:**

```bash
python3 -m pytest -q
```

**Каждое изменение — отдельный коммит:**

```bash
git add -A && git commit -m "что изменил"
```

**Если что-то сломалось — вернуться:**

```bash
git diff                  # что изменилось
git checkout -- файл.py   # откатить один файл
git reset --hard HEAD     # откатить всё до последнего коммита
git log --oneline         # история
```

**Что нельзя коммитить:** `.env` и `*.db`. Они в `.gitignore`, но лучше
проверять: `git status` перед коммитом.

## Ошибки, которые тесты уже поймали

Не для истории, а чтобы не повторить:

- падение при записи нового агента: поле `dm_open` объявлено `NOT NULL`,
  а вставлялось пустым;
- `7 999 123 45 67` без плюса читалось как код страны +7 плюс ещё один
  номер;
- служебный этап воронки, который amoCRM отказывается принимать при
  создании сделки;
- потеря языка между карточкой и подтверждением: в обработчике два блока
  данных заявки, язык кладли только в один;
- обрезка размеченного текста по длине рвала HTML-тег, и превью рассылки
  падало молча.
